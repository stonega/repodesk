# 定时任务与报告

用定时任务定期执行文字描述的请求，例如提醒、聊天总结或仓库报告，并发送到指定位置。当前支持每日和每周重复，不支持任意 cron 表达式或持续监控所有事件。

定时任务不要求先创建或批准技能。**Skill** 可以留为 **No skill**；需要复用特定技能时再选择，执行会固定该技能的发布版本。没有选择技能的任务不会因其他技能停用而挂起。

定时不会增加工具或数据源。天气等实时信息仍需可用且获准的数据工具；缺少数据时，机器人应说明具体缺口，不能编造报告。访问权限、审批和预算仍然适用。

## 创建定时总结

在已关联群中明确提出：

> 每周五 17:00 Asia/Taipei 总结这个群过去七天的讨论，按决策、阻塞、待办排列，发到本 Topic。

机器人展示提案。确认以下内容后，由请求本人在十五分钟内点击 **Approve**：

- 谁负责此任务。
- 读取哪个群、Topic 或仓库，以及时间范围。
- 输出到哪里，哪些人会看到。
- 时区、预算、格式和接下来的三个执行时间。

**Reject** 放弃，过期后重新提出。时间或接收位置不清楚时，先补充信息。定时任务的创建与日常聊天不同，描述需求不代表已经激活。

## 定期 GitHub 报告

例如：

> 每天 09:00 Asia/Taipei 给我一份 example/app 的 PR 报告，列出待审查、已合并和阻塞项，附链接。

工作区需先 [连接 GitHub](github.md)。报告会固定批准的仓库来源与目的地。私人仓库信息发送到群组时，需要工作区管理员检查并批准其披露范围；不要直接把私聊读取权限当作群分享许可。

GitHub 元数据可以生成报告，但不表示可以持续访问任意网站或使用所有插件。Cloudflare 工具和自动长期记忆不用于这些定时运行。

## 在面板管理

打开 **Workflows**，可以创建、查看、编辑、审批和暂停任务。修改会使用版本化提案，核对新的时间与范围后再批准。多个管理员同时修改导致保存冲突时，先重新加载核对。

Telegram 命令：

```text
/automations
/automations pause <任务 UUID>
/automations resume <任务 UUID>
/automations run <任务 UUID>
/automations delete <任务 UUID>
```

操作需要任务对应权限。暂停后不再触发新的运行；恢复已暂停任务与重新授权被撤权而挂起的任务不同，后者需要重新审批。

## 调整输出

Reply 一条定时输出：

```text
/correct once 这次改成中文，并把阻塞放在最前面
```

只生成一次纠正后的结果，不修改未来规则。希望持久生效时：

```text
/correct save 后续都使用中文，先列阻塞，再列决策和待办
```

核对并批准持久纠正。未来运行使用新规则，已经执行中的任务保留开始时的版本。也可在面板管理工作流指令。

## 时间、失败和恢复

- 使用 IANA 时区，例如 `Asia/Taipei`，不要只写可能有歧义的“周五下午”。涉及夏令时时核对显示的执行时间。
- 延迟超过五分钟的计划会跳过，恢复服务后不会集中补发大量过期输出。
- 所有者失去资格、选用的技能被停用等情况会挂起相关工作，需要处理原因并重新批准。
- 模型成功与消息成功交付是两种状态。在 **Runs & delivery** 分别检查。
- Telegram 发送结果未知时，先确认群内是否已有消息，不会自动重复发送。

群总结能覆盖多少消息取决于 [群组收集设置](groups.md) 和保留期限；不能补读 Telegram 旧历史。预算失败或无人收到报告时，参阅 [排障指南](troubleshooting.md)。
